# ローカル開発環境構築手順書
## 1. ローカル開発環境の基本方針

ローカル開発環境はDocker Composeを使用して構築する。

- フロントエンド（React / Node.js）
- バックエンド（Spring Boot / Java 21）
- データベース（PostgreSQL）

各実行環境をDockerコンテナ内に構築し、開発機にインストールされたJavaやNode.jsのバージョンに依存しない構成とする。

### 1.1 ソースコードの変更反映

開発効率を高めるため、ホットリロードを採用する。

- フロントエンド：ViteのHMRを使用する。
- バックエンド：Spring Boot DevToolsを使用し、変更を検知してアプリケーションを再起動する。
- ソースコードはDockerのバインドマウントでコンテナに共有する。

これにより、通常のソースコード変更時にコンテナイメージを再ビルドする必要をなくす。

### 1.2 データベースの永続化

PostgreSQLのデータは、Dockerの名前付きボリュームに保存する。

コンテナの停止・削除・再作成を行っても、データが保持される構成とする。

開発用データの初期化は、明示的な操作で行う。

### 1.3 データベースの変更管理

データベースのスキーマ変更にはFlywayを使用する。

- テーブルの作成・変更はバージョン付きSQLファイルで管理する。
- マイグレーションファイルはGitでバージョン管理する。
- Flywayによって適用済みの変更履歴を管理する。
- 開発環境の構築時に、未適用のマイグレーションを実行する。

FlywayはSpring Bootに組み込み、アプリケーション起動時に未適用のマイグレーションを自動実行する。

マイグレーションSQLは `src/main/resources/db/migration/` に配置する。

### 1.4 ローカル開発環境の通信方式

ローカル開発環境ではHTTPを使用する。

外部ネットワークへの公開は行わず、開発機内での利用に限定する。

本番環境ではHTTPSを使用し、HTTPとHTTPSの違いによる認証・セッション管理への影響を試験時に確認する。

### 1.5 Webサーバー

ローカル開発環境でもNginxを使用する。

- NginxをDockerコンテナとして起動する。
- フロントエンドへのアクセスとバックエンドへのAPIリクエストをNginx経由にする。
- Nginxから各コンテナへの通信にはDocker内部ネットワークを使用する。
- ローカル環境ではTLS終端を行わず、HTTPで通信する。

### 1.6 フロントエンド開発サーバー

フロントエンドにはViteの開発サーバーを使用する。

- ViteはNode.jsコンテナ内で実行する。
- NginxからViteへリバースプロキシする。
- HMR（Hot Module Replacement）を有効にする。
- HMRで使用するWebSocket通信もNginx経由で転送する。
- フロントエンドのソースコードはバインドマウントで共有する。

### 1.7 バックエンドへのAPI通信

- ブラウザからのAPIリクエストは `/api/` を使用する。
- Nginxは `/api/` へのリクエストをSpring Bootコンテナへ転送する。
- フロントエンドとAPIは同一オリジンで提供する。
- Spring Bootのポートは開発機の外部に公開しない。

### 1.8 ローカル環境のアクセス先

ローカル開発環境では、Nginxを経由してアプリケーションにアクセスする。

- アクセスURL：`http://localhost:8080`
- Nginxの公開ポート：`127.0.0.1:8080`
- フロントエンド：`/`
- バックエンドAPI：`/api/`

Docker Composeでは、Nginxのポートを開発機のループバックアドレスにバインドし、外部ネットワークからのアクセスを防止する。

### 1.9 PostgreSQLへの接続

開発機からデータベース管理ツールを使用して、PostgreSQLへ直接接続できる構成とする。

- 接続先：`localhost`
- ポート：`5432`
- 公開範囲：`127.0.0.1` のみ
- 接続認証：ユーザー名とパスワード

Docker Composeでは `127.0.0.1:5432:5432` を指定し、外部ネットワークには公開しない。

認証情報は環境変数で管理し、Gitには登録しない。

### 1.10 Docker Compose設定ファイルの配置

ローカル開発環境のDocker Compose関連ファイルは、リポジトリ内の `infra/local/` に配置する。

```text
Feat/
├── documents/
├── infra/
│   └── local/
│       ├── compose.yaml
│       └── nginx/
│           └── default.conf
├── frontend/
└── backend/
```

フロントエンドとバックエンドのDockerfileは、それぞれのアプリケーションディレクトリに配置する。

### 1.11 バックエンドのビルドツール

バックエンドのビルドツールにはMavenを採用する。

- Java 21およびSpring Bootを使用する。
- 依存ライブラリは `pom.xml` で管理する。
- Maven Wrapper（`mvnw`）を使用し、ビルドツールのバージョンを統一する。
- ビルドおよびテストはDockerコンテナ内で実行する。

### 1.12 フロントエンドのパッケージ管理

フロントエンドのパッケージ管理にはnpmを採用する。

- 依存ライブラリは `package.json` で管理する。
- `package-lock.json` をGitで管理し、依存関係のバージョンを固定する。
- 開発環境の依存ライブラリのインストールには `npm ci` を使用する。
- npmコマンドはNode.jsコンテナ内で実行する。

### 1.13 フロントエンドのテストツール

フロントエンドの単体テストにはVitestを採用する。

Reactコンポーネントのテストには、必要に応じてReact Testing Libraryを使用する。

テストはNode.jsコンテナ内で実行する。

### 1.14 バックエンドのテストツール

バックエンドの単体テストにはJUnit 5を採用する。

- Spring Boot Testを利用する。
- テストはMavenで実行する。
- テスト実行環境はDockerコンテナ内に統一する。

### 1.15 コード品質管理

コード品質を維持するため、以下のツールを導入する。

| 対象 | ツール | 用途 |
|---|---|---|
| TypeScript / React | ESLint | 静的解析 |
| TypeScript / React | Prettier | コード整形 |
| Java / Spring Boot | Checkstyle | コーディング規約の検査 |

各ツールはDockerコンテナ内で実行する。

### 1.16 Javaコードの自動整形

Javaコードの自動整形にはSpotlessを採用する。

- MavenのSpotlessプラグインを使用する。
- コード整形ルールをプロジェクト内で統一する。
- Checkstyleによる静的検査と併用する。
- 整形・検証はDockerコンテナ内で実行する。

### 1.17 データベース連携テスト

バックエンドのデータベース連携テストにはTestcontainersを採用する。

- テスト用のPostgreSQLコンテナを起動する。
- 開発用データベースとは分離する。
- Flywayでテスト用データベースのスキーマを構築する。
- JUnit 5と組み合わせてテストを実行する。
- テスト終了後はテスト用コンテナを破棄する。

### 1.18 CI（継続的インテグレーション）

CIにはGitHub Actionsを採用する。

- Pushおよびプルリクエスト作成時に自動実行する。
- フロントエンド：ESLint、Prettier、Vitestによる検証
- バックエンド：Checkstyle、Spotless、JUnit 5による検証
- データベース連携テスト：Testcontainersを使用する。
- ワークフロー定義は `.github/workflows/` に配置する。

### 1.19 CIの実行条件

GitHub Actionsは、すべてのブランチへのPush、およびmainブランチを対象とするプルリクエストで実行する。

- アプリケーションコードや構築設定の変更時は、対応するテストと静的解析を実行する。
- `documents/` 配下のみの変更時は、アプリケーションのテストと静的解析を省略する。
- 文書とコードの両方を変更した場合は、必要なテストと静的解析を実行する。
- 必須チェックは文書のみの変更でも正常終了できる構成とする。

### 1.20 CIの並列実行

GitHub Actionsでは、フロントエンドとバックエンドの検証を独立したジョブとして並列実行する。

- フロントエンド：ESLint、Prettier、Vitest
- バックエンド：Checkstyle、Spotless、JUnit 5、Testcontainers

各ジョブの結果を個別に確認できる構成とする。

### 1.21 mainブランチの保護

GitHubのブランチ保護ルールを設定し、CIの成功を `main` ブランチへのマージ条件とする。

- 必須CIチェックが失敗した場合、マージを禁止する。
- CIが完了していない場合も、マージを禁止する。
- ドキュメントのみの変更でも、必須チェックが正常終了する構成とする。
- `main` への変更はプルリクエストを経由する。

### 1.22 ローカル開発環境の起動・停止

ローカル開発環境の起動・停止にはDocker Composeを直接使用する。

構成ファイルは `infra/local/compose.yaml` に配置する。

```bash
# 起動
docker compose -f infra/local/compose.yaml up -d

# 停止
docker compose -f infra/local/compose.yaml down

# 状態確認
docker compose -f infra/local/compose.yaml ps
```

コマンドはリポジトリのルートディレクトリから実行する。


### 1.23 コンテナのログ確認

各コンテナのログは標準出力・標準エラーに出力し、Docker Composeで確認する。

```bash
# 全コンテナのログを表示
docker compose -f infra/local/compose.yaml logs

# ログをリアルタイムに表示
docker compose -f infra/local/compose.yaml logs -f

# バックエンドのログのみ表示
docker compose -f infra/local/compose.yaml logs -f backend
```

コマンドはリポジトリのルートディレクトリから実行する。

### 1.24 コンテナの再起動方針

ローカル開発環境では、コンテナの自動再起動を設定しない。

- Docker Composeの `restart` ポリシーは `no` とする。
- 開発環境は必要なときに手動で起動する。
- コンテナの異常終了時は、ログを確認して原因を調査する。


### 1.25 コンテナの起動順序

PostgreSQLが接続可能な状態になってからSpring Bootを起動する。

- PostgreSQLに `healthcheck` を設定する。
- Spring Bootには `depends_on` の `condition: service_healthy` を設定する。
- PostgreSQLの接続準備が完了するまで、Spring Bootの起動を待機させる。

これにより、データベースの起動待ちによる接続エラーを防ぐ。

### 1.26 バックエンドのヘルスチェック

Spring Boot Actuatorを使用して、バックエンドの稼働状態を確認する。

- ヘルスチェックには `/actuator/health` を使用する。
- Spring BootコンテナにDockerの `healthcheck` を設定する。
- ヘルスチェック用エンドポイントは外部に公開しない。
- ヘルスチェック失敗時はコンテナの状態とログを確認する。

### 1.27 フロントエンドのヘルスチェック

Vite開発サーバーにDockerの `healthcheck` を設定する。

- HTTPリクエストへの応答で稼働状態を判定する。
- ヘルスチェックはコンテナ内部から実行する。
- 異常時はコンテナの状態とログを確認する。

### 1.28 Nginxの起動順序

Nginxは、フロントエンドとバックエンドが正常に起動してから起動する。

- ViteとSpring Bootのヘルスチェック成功を起動条件とする。
- Docker Composeの `depends_on` と `condition: service_healthy` を使用する。
- Nginx起動後は `http://localhost:8080` からアクセスする。

なお、起動後に各サービスが異常終了した場合の自動復旧は行わない。

### 1.29 環境変数の管理

ローカル開発環境の設定値は、環境変数で管理する。

- `infra/local/.env.example` に必要な環境変数の名前と設定例を記載する。
- 実際の設定値は `infra/local/.env` に記載する。
- `.env` は `.gitignore` でGit管理から除外する。
- パスワードや秘密鍵などの機密情報をGitに登録しない。
- `.env.example` に実際の認証情報を記載しない。

### 1.30 Dockerイメージのバージョン管理

Dockerイメージは、バージョンを明示して使用する。

- 原則として、最新に近い安定バージョンを採用する。
- `latest` タグは使用しない。
- バージョン更新時は互換性と動作を確認する。
- 重大な脆弱性に対するセキュリティ修正や緊急修正（Hotfix）が公開された場合は、速やかに更新・検証する。
- バージョンの変更履歴はGitで管理する。

### 1.31 依存ライブラリのバージョン管理

Java（Maven）およびTypeScript（npm）の依存ライブラリは、以下の方針で管理する。

- 原則として、最新に近い安定バージョンを採用する。
- バージョン更新時は互換性を確認し、テストを実施する。
- 重大な脆弱性や緊急修正（Hotfix）には速やかに対応する。
- 依存関係の変更履歴はGitで管理する。

### 1.32 Dependabotによる依存関係の更新

依存ライブラリの更新管理にはGitHub Dependabotを使用する。

- Maven、npm、GitHub Actions、Dockerの依存関係を監視する。
- 安定版への更新を検出し、更新用プルリクエストを自動作成する。
- 重大な脆弱性や緊急修正には速やかに対応する。
- 更新内容はCIで検証し、確認後にマージする。
- 設定ファイルは `.github/dependabot.yml` に配置する。
- 自動マージは行わない。

Dependabotによる依存関係の定期更新チェックは週1回とする。

セキュリティ上の脆弱性への対応は定期更新とは別に扱い、重大な問題には速やかに対応する。

### 1.33 Dockerイメージのビルド

ローカル開発環境では、Docker Composeを使用してアプリケーションのイメージをビルドする。

- フロントエンドは `frontend/Dockerfile` からビルドする。
- バックエンドは `backend/Dockerfile` からビルドする。
- PostgreSQLとNginxは公式イメージを使用する。
- ビルド設定は `infra/local/compose.yaml` で管理する。

```bash
docker compose -f infra/local/compose.yaml up -d --build
```

### 1.34 開発用初期データの登録

ローカル開発環境では、動作確認用の初期データを自動登録する。

- 開発用ユーザー、プロジェクト、メンバー、タスクなどを用意する。
- 初期データはローカル開発環境専用とする。
- データベースのスキーマ管理にはFlywayを使用する。
- 初期データを重複登録しない仕組みを設ける。
- 本番環境には開発用データを登録しない。

### 1.35 開発用初期データの投入方法

開発用初期データはSpring Bootの初期化処理で登録する。

- Spring Profile `local` の場合のみ実行する。
- Flywayによるスキーマ構築後に実行する。
- 初期データの重複登録を防止する。
- 開発用ユーザーの認証情報は本番環境で使用しない。
- 本番環境では初期データ投入処理を無効にする。

### 1.36 開発用データベースの初期化

ローカル開発環境に、開発用データベースを初期状態へ戻す手順を用意する。

- 専用コマンドで開発用DBを初期化する。
- 初期化後、Flywayでスキーマを再構築する。
- Spring Bootの初期化処理で開発用データを再投入する。
- 誤操作防止のため、初期化前に確認操作を要求する。
- 本番環境では初期化コマンドを実行できない構成とする。

初期化すると既存の開発用データが失われるため、必要に応じてバックアップを取得する。

### 1.37 データベース初期化スクリプト

ローカル開発環境のDB初期化には、専用シェルスクリプトを使用する。

- 配置先：`infra/local/reset-db.sh`
- 実行前に確認メッセージを表示する。
- ローカル開発用PostgreSQLのデータのみを初期化する。
- 初期化後、Flywayでスキーマを再構築する。
- Spring Bootで開発用初期データを再投入する。
- 本番環境では実行できないようにする。

### 1.38 開発用データベースのバックアップ・復元

ローカル開発環境では、PostgreSQLのバックアップ・復元を手動で実行できるようにする。

- バックアップには `pg_dump` を使用する。
- 復元には `pg_restore` を使用する。
- コマンドはPostgreSQLコンテナ内で実行する。
- バックアップファイルはGit管理対象外とする。
- 復元前に対象データベースを確認し、誤操作を防止する。

### 1.39 バックアップ・復元スクリプト

ローカル開発用PostgreSQLのバックアップ・復元には、専用シェルスクリプトを使用する。

- バックアップ：`infra/local/backup-db.sh`
- 復元：`infra/local/restore-db.sh`
- バックアップには `pg_dump` を使用する。
- 復元には `pg_restore` を使用する。
- 復元前に確認操作を要求する。
- バックアップファイルはGit管理対象外とする。
- 本番環境のデータベースは操作対象としない。
- バックアップは必要に応じて手動で取得し、定期的な自動バックアップは行わない。

### 1.40 バックアップファイルの保存先

ローカル開発用データベースのバックアップファイルは、`infra/local/backups/` に保存する。

- バックアップスクリプトは、このディレクトリにファイルを出力する。
- `infra/local/backups/` は `.gitignore` でGit管理から除外する。
- バックアップファイル名には取得日時を含め、複数世代を保存できるようにする。
- バックアップファイルの自動削除は行わず、不要になったファイルは手動で削除する。

### 1.41 バックアップの復元確認

バックアップの復元試験には、開発用DBとは別の一時データベースを使用する。

- 復元先には専用の一時データベースを作成する。
- `pg_restore` の正常終了を確認する。
- 必要なテーブルの存在と、復元データの件数・内容を確認する。
- 開発用DBの既存データには影響を与えない。
- 確認完了後、一時データベースを削除する。

通常の復元操作では、対象データベースを確認してから実行する。

### 1.42 バックアップ復元試験の自動化

バックアップの復元試験には、専用シェルスクリプトを使用する。

- 配置先：`infra/local/verify-backup.sh`
- 復元試験用の一時データベースを作成する。
- 指定されたバックアップファイルを復元する。
- テーブルの存在とデータ件数を検証する。
- 検証結果を表示する。
- 試験終了後、一時データベースを削除する。
- 開発用DBおよび本番DBには変更を加えない。

### 1.43 開発環境の動作確認

ローカル開発環境の正常動作を確認するスクリプトを用意する。

- 配置先：`infra/local/verify-environment.sh`
- Nginx・Vite・Spring Boot・PostgreSQLの稼働状態を確認する。
- 検証結果を表示し、異常がある場合はエラーを返す。

### 1.44 CPUアーキテクチャへの対応

ローカル開発環境は、AMD64およびARM64の両方に対応する。

- Dockerイメージは両アーキテクチャに対応したものを採用する。
- 原則として、開発機に適したアーキテクチャのイメージを自動選択する。
- 特定のCPUアーキテクチャに依存する設定を可能な限り避ける。


### 1.45 対応OS

ローカル開発環境は、macOS・Windows・Linuxに対応する。

- Docker Composeを共通の実行基盤とする。
- WindowsではWSL2の利用を前提とする。
- 構築手順はOS固有の設定を可能な限り避ける。
- シェルスクリプトはmacOS・Linux・WSL2で実行できるようにする。


### 1.46 初回セットアップ方式

ローカル開発環境の初回セットアップは、構築手順書に従って実施する。

- 各工程のコマンドを順番に実行する。
- 実行結果を確認してから次の工程に進む。
- Docker Composeを使用して各サービスを構築・起動する。
- 初回セットアップ専用の一括実行スクリプトは作成しない。

### 1.47 開発環境の再現性

ローカル開発環境は、対応OS・CPUアーキテクチャの異なるPCでも再現可能な構成とする。

- Gitで管理された設定ファイルと構築手順書から環境を構築できること。
- 開発機固有の設定やパスに依存しないこと。
- 各サービスの起動と動作確認が成功すること。
- 別のPCでの構築検証を実施し、結果を記録すること。
